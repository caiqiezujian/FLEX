# 四卡多轮同步死锁：原因、修复与复测

> 本文记录之前的同步故障及修复；当前QALCO v2在保留该生产补丁的基础上增加EOF收尾，相关四rank模拟已追加EOF覆盖。当前奖励与3000步/每500步保存配置以README及QALCO方案为准，下面“未改变奖励”等描述仅指当时那次同步修复。

本次只修正在线多轮 rollout 的分布式退出同步与可观测性。SFT 提示词、数据切片、WAIT/FLEX/DIRECT 输出协议、QALCO 奖励、GSPO 损失和模型并行配置不变。

## 1. 已定位的原因

服务器使用 Megatron TP2、EP2，以及 vLLM TP4 的 colocate 推理。用户提供的四个进程堆栈显示：

| 进程 | 停留位置 | 正在等待 |
| --- | --- | --- |
| rank 0、1 | `_colocate_rollout` → `all_gather_object` | 下一轮四卡推理的请求汇总 |
| rank 2、3 | `_log_completions_from_samples` → `gather_object` | 轨迹已结束后的全局日志汇总 |

上游该提交在 `run_multi_turn` 中使用 Megatron rollout group 判断是否全部完成；本配置该组只有两个进程。但实际推理的请求汇总使用四进程的 `vllm_tp_group`。当两组音频长度、非法输出早停或其他结束条件不同，短组会先退出，多轮推理所需的四个参与者随即不再执行同一组通信。

这不是“第一步只是比较慢”，也不是 `sampling_rate: None` 这一日志造成的。关闭 completion 日志只会移动后续等待的位置，不能修复提前退出。缩小 batch 或恰好换成同长度音频，也不能保证消除问题。

源码审查依据为固定提交 `modelscope/ms-swift@f15bb91439d756d4a366b51956d72d1f088b7af6` 的 `swift/megatron/trainers/rollout_mixin.py` 和 `swift/rollout/agent_loop.py`。

## 2. 修复方式

项目增加 `flex_gspo/rollout_sync.py`，在 `FlexStreamScheduler` 初始化时安装进程内兼容包装：

1. 仅在 FLEX scheduler + Megatron colocate 的 `_generate_completions` 中记录当前 trainer 上下文。
2. 仅替换该调用传给原始 `run_multi_turn` 的 `gather_fn`；实际多轮驱动继续由 SWIFT 执行。
3. vLLM TP 大于 1 时，完成判定使用 **trainer 已创建的真实 `vllm_tp_group`**，与 `_colocate_rollout` 一致；TP1 则使用本地判定，不意外进入默认全局组。
4. 本地已完成的进程仍以空请求 `[]` 参加原始 rollout 通信，直到整个 vLLM 组都结束。
5. 不修改 `_get_rollout_group()`，因此 Megatron 数据分片、输出合并和组内优势计算没有被扩成四卡。
6. 包装支持重复安装检查、异常后上下文恢复；初始化时不读取尚未创建的 GPU group。预检通过 AST 核对关键调用契约，契约变化时报明确错误，不静默跳过修复。

没有改写服务器 `site-packages`，没有覆盖原始 token、log-probability 或 loss mask，也没有合成额外回答。上游结束前的一次全空 rollout 被保留。非 FLEX 及 Megatron 内的 server 路径不替换其完成判定；本项目仍只验收 colocate 方案，并不因此声明独立 server 部署已支持。

## 3. 上传与重启范围

运行文件的变化是：

- `flex_gspo/rollout_sync.py`：新增同步兼容模块，必须一起上传。
- `swift_plugin.py`：自动启用兼容模块。
- `check_environment.py`：增加源码调用契约检查。
- `train_megatron.py`：增加 `--rollout-log-every`，默认 5。
- `flex_gspo/online_reward.py`：增加奖励阶段开始/结束日志，不改变计算。

另外更新了 README、本文、验证记录，并增加回归测试。可以同步整个 `FLEX-GSPO` 目录，但请保留服务器自己已经配置好的 `configs/default.json` 或独立奖励配置文件。

先在原训练终端中停止本次卡住的任务，确认该任务的四个训练进程已经退出，再启动复测。不要杀其他任务或占用 GPU 4–7 的服务，也不必重启 Docker。已经运行的 Python 进程不会自动加载上传后的修复。

无需重新切音频、重新 prepare 或重新离线生成轨迹。已准备好的 `train.jsonl`、原音频和 SFT checkpoint 可以原样使用。本次也不要求重装 SWIFT/CUDA 环境。

解释器应是 `/data/yb/venvs/flex-gspo-online/bin/python3`。若仍显示 `/data/miniconda3/bin/python3`，先回到正确容器与虚拟环境，不要在宿主机重新安装训练包。

这里沿用 G8、B32，避免靠改变 batch 掩盖同步问题。输出目录必须是新的；如果 `gspo_syncfix_001` 已有实验结果，换新名称，不覆盖旧结果。该补丁会改变代码身份哈希，不应在旧卡死目录上强行恢复。旧任务尚未完成第一个更新，本次从同一个 SFT checkpoint 开始即可。

## 5. 如何判断有进展

日志包含 rank，多个进程的输出可以交错；下列是字段示意，不是保证每次都严格按这一行序出现：

```text
[FLEX rollout][rank=0] patch_installed id=flex-vllm-group-termination-v1 ...
[FLEX rollout][rank=0] generation_begin ...
[FLEX rollout][rank=0] sync_ready ... completion_group_size=4 ...
[FLEX rollout][rank=0] completion_check_begin round=... local_active=...
[FLEX rollout][rank=0] completion_check_end round=... active_ranks=2/4 all_done=False
[FLEX rollout][rank=0] continuation_begin call=... local_requests=0
[FLEX rollout][rank=0] continuation_end call=... local_outputs=0 elapsed=...
[FLEX rollout][rank=0] completion_check_end round=... active_ranks=0/4 all_done=True
[FLEX rollout][rank=0] generation_end local_trajectories=... elapsed=...
[FLEX rollout][rank=0] reward_begin local_candidates=...
[FLEX rollout][rank=0] reward_end local_candidates=... elapsed=...
```

`local_requests=0` 与 `active_ranks=2/4` 同时出现是正常的：本地候选已结束，但还有同组候选需要继续读音频。四个进程都结束后再进入后续阶段。不要把 `sync_ready` 当作整步训练已经成功；它只证明修复进入了指定路径。

验收要同时确认：

- 出现 `completion_group_size=4`，所有 rank 都能结束多轮生成。
- 奖励阶段完成，训练从 `0/2` 推进到两个优化步骤，损失/梯度无非有限值。
- 第二批 rollout 正常执行，保存步骤完成，并检查实际 checkpoint 产物。
- 不能仅凭 GPU 利用率、加载成功或终止日志判断训练验收完成。

如果再次停住，保留每个 rank 最后的阶段日志和原始异常即可据此缩小范围：`generation_begin` 后尚未 `sync_ready` 属于首轮之前/首轮路径；停在 `continuation_begin` 表示本轮推理未返回；只有 `reward_begin` 则表示评分阶段尚未返回。不要先更换奖励公式或屏蔽真实异常。

## 6. 本地验证边界

CPU 回归用四个模拟进程参与者、真实上游多轮循环和项目 scheduler 复现原两进程退出范围的错误，再验证生产 `make_completion_gather` 的修复。包括不等长轨迹、初始空请求、无效输出提前终止，以及 token/mask/logprob 保持不变。安装包装器和非目标路径另有单元测试。

这些测试不需要模型，也没有运行真实 NCCL、A800 推理或优化器。当前结论是“根因已定位、对应代码已修正并完成 CPU 回归”，不是“服务器四卡训练已经验收”。完整测试结果见 [验证与清理记录](验证与清理记录.md)。
