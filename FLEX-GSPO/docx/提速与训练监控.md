# FLEX 在线 GSPO：保留稳定版的提速与监控

## 1. 这次改变了什么

用户已报告 G8/B32 的四张 A800 两步训练成功。这里保留该配置，另加可选试验入口，不替换 SWIFT/Megatron/vLLM，也不改变 QALCO 公式或 WAIT/FLEX/DIRECT 协议。

| 配置 | 稳定入口 `03_train_4100.sh` | 可选入口 `04_train_throughput.sh` |
| --- | --- | --- |
| 每条音频候选数 | 8 | 8 |
| global batch | 32 | 32 |
| micro batch | 1 | 2 |
| steps per generation | 1 | 1 |
| vLLM max_num_seqs | 16 | 32 |
| vLLM GPU 显存预算 | 0.40 | 0.50 |
| 训练步数 / 保存间隔 | 4100 / 100 | 4100 / 100 |
| 阶段 JSONL 计时 | 默认关闭 | 默认开启 |

没有改：Megatron TP2/EP2、vLLM TP4、完整重计算、eager、sleep2、模型/优化器 offload、全权重同步、LoRA、KL、学习率、奖励配置、数据和音频路径。也没有打开此前导致音频重编码报错的框架 `log_completions`。

增大真实并发才可能把空闲显存换成吞吐；单纯增加 global batch 只会增加每次更新的工作量。vLLM 的 0.50 是该推理实例的预算，不是整个进程的显存上限，也不是 GPU 算力利用率。训练激活、同步临时张量和保存阶段的峰值仍需实测。**不能保证新配置不 OOM，更不能把“没有语法错误”说成 GPU 已验收。**

## 2. 先做 5 步独立验证

在原来已经跑通的 Docker 和虚拟环境中执行。不要在正在运行的实验目录上覆盖代码或混写输出；先等旧任务结束，或按自己的计划停止它。不要让新旧两个训练任务竞争同样四张卡。

```bash
cd /data/flex/FLEX-GSPO
source /data/venvs/flex-gspo-online/bin/activate

bash 04_train_throughput.sh \
  /data/models/flex-sft-merged \
  /data/flex/datasets/gspo_online_prepared_clean/train.jsonl \
  /data/flex/outputs/gspo_throughput_check_001 \
  --train-iters 5 \
  --save-steps 5
```

末尾加 `--dry-run` 可只检查参数；不会启动训练、创建输出目录或访问 MetricX。路径是直接位置参数，文件夹名字可自行替换。新目录不得与之前实验混用。

验证重点：连续优化步骤完成、loss/梯度有限、后续生成成功、真实 checkpoint 保存成功、无新的 OOM/通信挂起；比较第 2～5 步而不是只看包含初始化/首次缓存的第 1 步。两边应保持相同 G、global batch、输入预算、随机种子及数据，以相同候选数量的墙钟耗时衡量吞吐，不能只比较显存填满比例。样本长度差异会影响每步时间。

如果需要逐项定位，可在 `03_train_4100.sh` 后依次单独追加 `--vllm-max-num-seqs 32`、`--micro-batch-size 2`、`--vllm-memory 0.50` 做新目录对照，另加 `--performance-log on` 获得相同计时。不同阶段的 A/B 试验都应使用新输出目录。

## 3. 验证通过后正式 4100 步

```bash
bash 04_train_throughput.sh \
  /data/models/flex-sft-merged \
  /data/flex/datasets/gspo_online_prepared_clean/train.jsonl \
  /data/flex/outputs/gspo_throughput_4100_001
```

这仍然是每次更新计划 4 条音频任务、共 32 条候选；4100 步计划 16,400 次音频抽样及 131,200 条候选，不是 25 万条数据完整一遍。开始正式实验时从已验收的 SFT 合并权重出发；不能把 5 步试验的学习率计划当作 4100 步原样恢复。保留全部旧实验和原始数据。

若新配置显存不足或没有收益，使用 `03_train_4100.sh` 和另一个新输出目录即可恢复稳定参数；也可给 `04` 末尾追加 `--micro-batch-size 1 --vllm-max-num-seqs 16 --vllm-memory 0.4 --performance-log off`。不要为提速移除 KL 或放宽奖励门槛。

现有恢复检查还会验证代码哈希和训练参数。本次更新代码或更改 batch 后，不应绕过检查强行续接旧实验 checkpoint；如需原样继续旧实验，请保留它的原代码、参数及目录。新试验使用新目录，不删除既有模型/日志。单独查看旧日志可以直接启动监控，不必重启原训练。

额外提供 `--recompute-granularity selective` 作为后续独立试验，默认仍为 `full`。选择 selective 时启动器不会再传与它冲突的 `recompute_method` / `recompute_num_layers`。它可能减少反向重算，但增加显存，仍须重新做服务器验证；第一档不要与其他未验证调整一起开启。

G8、DP2、steps=1 时，micro=2 可搭配 B32/B64，不能搭配 B48。B64 会增加每步工作量，不能承诺单步更快。当前不开放自动改变 TP/EP、睡眠、offload 或 LoRA-only 同步的“一键提速”，以免再次引入未经验证的执行路径。

## 4. 监控是独立进程，不进入训练计算

原有 `report_to=tensorboard` 已启用。框架训练指标通常在输出目录的 `vN-时间/runs/`；同级 `logging.jsonl` 保存文本日志。新增监控读取 `rewards/rewards-rank*-pid*.jsonl` 和可选 `performance/performance-rank*-pid*.jsonl`，只往 `monitor/` 写派生文件。

在第二个终端、同一个环境执行：

```bash
python3 monitor_training.py \
  /data/flex/outputs/gspo_throughput_check_001 \
  --watch \
  --poll-seconds 10 \
  --max-samples 2 \
  --dataset /data/flex/datasets/gspo_online_prepared_clean/train.jsonl \
  --gpu-ids 0,1,2,3
```

`--dataset` 仅用于按 task_id 对照原文和机器参考，不加载 WAV，也不把文本输入训练模型。`--gpu-ids` 可省略；指定时仅通过 nvidia-smi 读取这些设备的显存与利用率。它们是定时采样的整卡读数，不是精确训练峰值，也可能包含同卡其他进程。

不加 `--watch` 时只导出目前已经写完的记录；因此也能查看之前正在运行或已经完成的实验。半行写入等到下一次轮询，不把它当损坏记录。中断监控不会中断训练。

默认在每个 rank/PID 的第 1、10、20……次奖励回调展示最多 2 条候选；不是只展示整个训练最开始的 2 条。可用 `--sample-every 1` 每次回调展示，或 `--max-samples 0` 关闭文本展示。单条页面文本最多 24,000 字符，完整内容始终保留在原奖励 JSONL。展示频率不影响训练或评分。`monitor/summary.latest.json` 可直接读取最近的分项摘要。

一批奖励可能尚未写完，同一横坐标可能出现局部累计快照；TensorBoard 不保证用后一个点覆盖前一个点，它们不能当作不同批次或完整 G8 组均值。正常退出重启会用游标跳过已导入记录；若观察器恰好在事件写入和游标保存之间崩溃，最后部分可能重放，不宣称事务级恰好一次。不同实验目录不能混用游标。

在第三个终端启动 TensorBoard，logdir 指向整个实验目录：

```bash
python3 -m tensorboard.main \
  --logdir /data/flex/outputs/gspo_throughput_check_001 \
  --host 0.0.0.0 \
  --port 6006
```

浏览器访问 `http://服务器地址:6006`，前提是容器端口/内网访问已经配置。这个命令没有身份验证，只在受信任内网使用；无需远程访问时改为 `--host 127.0.0.1`。不要为开监控端口重建或停止正在训练的 Docker；必要时使用现有网络通道/端口转发。正式训练后，把上面两个命令的实验目录换成正式目录。

若提示缺少 tensorboard，只在原训练虚拟环境内补装展示依赖，不升级 torch/CUDA/vLLM/ms-swift：

```bash
python3 -m pip install 'tensorboard>=2.14,<3'
```

监控直接使用 TensorBoard event writer，不导入 torch，不加载评分模型，不调用 MetricX。监控故障与训练进程隔离；保留原始日志可重建展示。不要同时启动两个监控实例写同一个派生目录。

## 5. 哪些曲线和输出值得看

| 观察项 | 意义与边界 |
| --- | --- |
| 框架 loss、grad_norm、learning_rate | 判断优化是否数值正常；GSPO loss 不是 SFT 交叉熵，不要求单调下降或一定大于 0 |
| 框架 reward_std、frac_reward_zero_std | 后者用于判断完整 G 组奖励是否退化；组内全同奖励会削弱奖励优势信号，不能用单 rank 的方差冒充完整 G 组 |
| 框架 KL、clip_ratio | 判断策略变化与更新裁剪；不要仅为让曲线“漂亮”关闭 KL |
| MetricX error | 越低越好；这是机器评分代理，不是人工准确率 |
| quality | 当前是 `1 - MetricX error / 25`；越高越好 |
| latency_seconds | 当前默认 mean-lag 源时间轴代理，越低越好；不是 GPU 实际推理耗时 |
| length_penalty | 超过参考长度预算才触发；大量为零未必是错误，不能把它直接解释成自然度 |
| quality_fail / latency_fail / feasible / invalid 比例 | 检查奖励门槛在哪一层起作用；若几乎全部卡在同一层，要查看原始译文和分数再决定，不自动改门槛 |
| WAIT / FLEX / DIRECT 比例、首出时间、最大无文字间隔、EOF 文字比例 | 检查是否长期等到结尾、过早输出或动作坍缩；标签比例本身不是质量得分 |
| Text 样本的原文、参考、候选、每轮增量和奖励项 | 判断“更简洁”是否只是漏译，“更低延迟”是否只是提前胡说；参考是机器翻译，不能替代源语音事实 |

原始奖励记录的 `global_step` 是评分发生时、更新前的步号；它和完成该次更新后框架的 loss 步号可能差 1。多个 rank、多个 PID 的记录各自展示，不把同一个 step 多次回调误认成多次优化更新。缺少 step 时使用明确标注的本地 callback 横轴，不伪造训练步号。

文本用于展示，保留已采样的模型原始输出，不重新生成或“修正”译文。日志/页面包含训练文本，应按训练数据权限保存，不要直接公开 TensorBoard 端口或上传日志。

## 6. 如何定位速度瓶颈

新增阶段计时均是主机墙钟，不同步 GPU、不改变 collective 顺序。重点区分：

- `generation_seconds`：一批完整多轮生成的总时长，含前后处理、权重同步与搬运等。
- `weight_sync_seconds`：训练权重到 vLLM 的同步调用。
- `rollout_requests_seconds` / `rollout_requests_count`：首轮及 continuation 请求调用的合计；包含组内通信、处理和推理等待，不是纯 GPU decode 时间。
- `offload_to_cpu_seconds` / `reload_to_gpu_seconds`：生成阶段前后的卸载与回载。

这些均按 rank 记录；不要把四个 rank 的时间加起来当成用户等待时间，也不要把非同步主机计时称为精确 kernel 耗时。阶段子项不一定覆盖所有总时长，未归类部分可包含前处理、唤醒、休眠和框架工作。实际完整更新还包含质量评分、logprob/reference 前向、反向和优化器等，要结合框架步骤日志观察。

若生成占主导，优先观察推理并发和阶段同步；若更新占主导，再评估 micro batch/重计算。不要仅提高显存预算就断言算力利用率提高，更不要删除真实流式轮次来制造表面加速。
