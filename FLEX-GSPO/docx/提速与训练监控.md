# QALCO v2：3000步训练、性能与监控

本文件对应COMET22 + EOF新轮次。完整命令及服务验收见 [README](../README.md)。上一轮卡死记录是诊断依据，不能把当时两步成功当作新版的长期稳定证明。

## 1. 两个参数入口

| 项目 | 03_train_3000.sh | 04_train_throughput.sh |
|---|---:|---:|
| 每条音频候选数 | 8 | 8 |
| global batch | 32 | 32 |
| micro batch | 1 | 2 |
| steps per generation | 1 | 1 |
| vLLM max_num_seqs | 16 | 32 |
| vLLM显存预算 | 0.40 | 0.50 |
| 总步数 | 3000 | 3000 |
| 周期保存 | 500 | 500 |
| 多模态processor cache | 0 | 0 |
| 性能JSONL | 开 | 开 |

04沿用上一轮实际使用的micro2配置，没有再扩大优化器batch。TP2/EP2、vLLM TP4、full recompute、eager、sleep2、模型及优化器offload、LoRA和KL不变。

vLLM内存比例是推理预算，不是整个训练进程的显存上限。此前日志报告过约78GiB峰值，瞬时35～41GB或sleep后的8GB不能作为关闭offload的依据。新增EOF也会增加上下文和一次生成调用；不能承诺固定提速倍数。

## 2. 保留的故障规避

- 多轮调度按真实vLLM TP组协调完成，已结束rank继续参加必要collective。
- 默认vllm_mm_processor_cache_gb=0，绕开已观察到的cachetools/vLLM清理路径；不改cachetools包、不关闭KV prefix缓存。
- 保持log_completions=false，不让框架为打印文本而遗漏音频重编码。
- 四卡训练与COMET22服务分离；有限重试后评分服务仍失败就报错，不制造奖励或无限等待。
- 启动前校验prepared任务、EOF轮数、服务基本正误排序、环境与checkpoint。
- 新reward日志带run/session identity，避免混合重启后的PID文件。

这些规避和CPU测试没有证明服务器以后绝不会失败。要观察超过此前68步失效点，检查phase日志是否持续推进，不能只看GPU利用率100%。

## 3. 正式命令

先完成README中的服务与短验收，再用新目录：

~~~bash
cd /data/yb/Code/FLEX/FLEX-GSPO
source /data/yb/venvs/flex-gspo-online/bin/activate

bash 04_train_throughput.sh \
  /data/data_process/lzy/qwen3_omni_mega/train/megatron_output/Qwen3-Omni-Flex/v3-20261016-172842/checkpoint-4410-merged \
  /data/yb/FLEX/datasets/gspo_online_prepared_clean/train.jsonl \
  /data/yb/FLEX/outputs/gspo_comet22_g8_b32_3000_001 \
  --train-iters 3000 \
  --save-steps 500 \
  --max-turns 65 \
  --vllm-mm-processor-cache-gb 0 \
  --performance-log on
~~~

两步smoke用独立目录并明确覆盖train/save参数；不可把2步LR周期checkpoint当作3000步无缝恢复。3000步正式轮次从原SFT起跑。每500步保存意味着此前无周期checkpoint，保存上限3意味着旧checkpoint可能按框架策略轮换。

同一正式轮次恢复必须使用真实原生checkpoint、相同3000步总周期、数据/奖励/代码身份；不能使用merged导出或旧v1训练状态。预留模型、原生optimizer/RNG分片及合并导出的磁盘。

## 4. TensorBoard

训练运行后，在另一个终端：

~~~bash
python3 monitor_training.py \
  /data/yb/FLEX/outputs/gspo_comet22_g8_b32_3000_001 \
  --watch \
  --dataset /data/yb/FLEX/datasets/gspo_online_prepared_clean/train.jsonl \

~~~

第三个终端：

~~~bash
python3 -m tensorboard.main \
  --logdir /data/yb/FLEX/outputs/gspo_comet22_g8_b32_3000_001 \
  --host 0.0.0.0 \
  --port 6006
~~~

也可在能读取同目录的其他环境运行监控，只需已有tensorboard和项目轻量依赖。它不加载Omni，不调用评分服务，不占训练GPU。注意端口映射和访问控制；不需要为此替换训练镜像。

## 5. 先看什么

| 指标 | 意义与警报 |
|---|---|
| 原始logging.jsonl更新时间、iteration | 持续推进比活进程和GPU100%更能说明在工作 |
| comet22_score、quality_pass_fraction | 质量代理及门槛情况，不是人工准确率 |
| empty_translation_fraction | 完整输入/收尾后仍无译文；按短音频/长音频分别抽查 |
| severe_repetition_fraction / degenerate | 严重精确循环是否被抓到、是否变多 |
| latency_seconds / eof_text_fraction | 是否拖到末尾；源时钟+固定EOF成本，不是实际墙钟延迟 |
| eof_generation_seconds | 本地宿主耗时，含排队/collective，不是单独GPU kernel时间 |
| actions/* | 仅音频轮的WAIT/FLEX/DIRECT比例 |
| eof_actions/* | 单独收尾轮动作；正常译完后WAIT不应当作全空失败 |
| reward_std / frac_reward_zero_std | 组内是否仍有可区分信号；没有信号不能靠把全组罚分等量加大解决 |
| KL / grad_norm / 非有限值 | 更新是否数值正常；不等于翻译提升 |
| performance中的generation/offload/reload/sync | 慢在哪里；未同步CUDA的host计时不是精确GPU性能剖析 |

各rank回调摘要不是完整全局G8组统计。只能在任务、prompt/candidate身份及步骤对齐后判断一组是否全WAIT，不能因为某个rank恰好有8条就这样下结论。

## 6. 如何判断是否真的变好

对固定验证音频比较SFT和新checkpoint：忠实性、数字/否定、漏译、自然度、循环重复、空输出、等待收益与时延。COMET22既然参与训练，必须配合人工抽查或其他未作为训练目标的证据，不能只用它宣布成功。MetricX可做旁路对照，但也不是绝对真值。

不要要求RL loss单调下降。不同音频难度、采样结果和组归一化都会改变loss与reward。训练窗口均值变化也不能替代同一验证集的对照。

本版没有逐WAIT反事实分支、语义对齐时延或VAD部署。EOF解决的是输入终止协议，不自动让原SFT理解所有短语境；真实输出仍需验收。
